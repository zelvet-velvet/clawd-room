## 🎬 The stage page: edit a part animation in the pixel editor (Zaviel)
> [!info] PR #19 (branch `feat/stage-page`)
- `./clawd-room.sh --edit anims/swing` (or `anims/brew`) opens the page picked in the mockups (layout B): the room with the thing on a stage and every part outlined, the picked part and its values at this frame beside it, the frames as pictures with a diamond under each key of the part, PLAY.
- Click a part to pick it; the MOVE and TURN tools drag it on the stage, KEY adds a key; `<` `>` beside a value change it at this frame (a key is made if there is none); keys for the rest (`?` shows them). Everything saves as you go to `~/.clawd-room/anims/`, and a room with a swinging Clawd follows your edit.
- Since the first try (Zaviel's notes): `q` asks like the editor (S save, D discard, Esc back); the tools work on the part pressed on; the view zooms (`+ -`, the wheel) and pans (`W A S D`, right drag); the panel, the frame strip and the help scroll; SELECT drags a part's border to resize it; the keys' marks on the stage can be switched off (`v`); TURN is called ROTATE, and is greyed for a sprite part (a Clawd moves, it does not rotate).
- Not yet: a tab for it in the sprite picker, onion skin, and rotation drawn in the room (parked).

## 🎢 The swing moves by a file: anims/swing.txt (Zaviel)
> [!info] PR #19 (nothing looks different)
- A Clawd on the playground swing now moves by `anims/swing.txt` (its `clawd` part) instead of a formula in the code. The file makes the same motion as before, to the pixel; change the keys and the swing changes while the room runs.
- Tested three ways: the swing scene is the same with the file as without it (the old formula is the fallback when there is no file), a bigger file makes a bigger swing, and the file's own poses are a snapshot. A scenario can start an emote (`emote T sid kind`), which no test could do before: the swing was never run by any of them.
- The chains turning and the seat moving, as in the mockups, are in the file too but not drawn yet: that is a new look, so it waits for a picked mockup.

## 🔧 Part animations: building starts with the file format (Zaviel)
> [!info] PR #19 (nothing to see in the room yet)
- A part animation is a text file in `anims/`: the parts of a thing and, for each, keyframes of where it is, how it is turned, whether it shows and its glow, with an ease between keys. `anims/swing.txt` (the park's swing) and `anims/brew.txt` (the barista brewing) are the first two.
- The program can load one and say where each part is at any time (a looping animation wraps; a key left out of a field keeps the earlier value; a file with a mistake names the line). The room does not draw these yet: next come drawing them, then the stage page in the editor ([[Interaction]]).
- Tested by a snapshot (`parts.txt`): the two files and a few good and bad ones.

## 🧩 Part animations in the pixel editor: the editor now, then the stage page (Zaviel)
> [!info] PR #20 (mockups; built in #19)
- Not only gates: a Clawd on the swing and the barista brewing are edited the same way. A thing is made of **parts**; each part has **keyframes** (where, how turned, whether it shows, its glow) and the engine moves it in between. It lives in the **current editor**, not a new tool.
- The mockups start from the editor as it is and change only what must change: the canvas shows the room instead of the sprite grid (as tall as the panel, as now), the tools are SELECT, MOVE, TURN and KEY on the same key caps, the panel shows the picked part and its values at this frame, the timeline keeps its line (name, ONION, 1X, PLAY) and the real-size view at its left.
- Two timelines were drawn: A, a dope sheet (a row per part); B, **the frames as pictures with a diamond under each keyframe** of the picked part. **B picked**: it is the timeline people know. The dope sheet comes later as a view switch; a gate gets a row per group of parts. Recorded in [[Interaction]].
